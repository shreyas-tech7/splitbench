**1. When is a split worth its cost?**

When the task is wide and the budget leaves room for every worker. Each worker then carries a short context, while one agent carries every document it has read, so the team spends fewer tokens for the same answer. When the budget is tight, each worker gets a slice too small to finish its share, and the lead combines partial reports. A chain never gains, because each hop waits for the one before it. See the decision guide:

**2. What is handoff loss, and how do you measure it?**

`metrics.handoff` takes the facts the task needs. It finds the ones that an upstream agent (a worker or the executor) saw in a tool result. Loss is the share of those that were missing from the final agent's context when it answered. A second number, `dropped`, is the share missing from the reports or evidence that were handed on. A fact can be dropped but not lost, when the checker reads the document again.

**3. Why must the budgets be equal?**

A design that spends more tokens reads more documents, so it can look smarter for that reason alone. Anthropic's own post says token use explained most of the gap in its tests. `budget.Budget` gives every design the same pool, and `agents.orchestrator` and `agents.pipeline` split that pool with `Budget.child`, so a team never gets extra.

**4. How do you prove no design goes over a cap?**

`Budget.reserve` checks the input and the requested output against what is left before a call, and grants at most the rest. `Budget.charge` counts the real output, cut to the grant. `tests/test_budget.py` runs every design at both levels with `SpamModel`, which asks for the full output every time, in lockstep and with threads. A version that checks after the call fails that test.

**5. What do the three MAST groups mean?**

FC1 is a specification or system design failure, such as a malformed answer or a loop. FC2 is a failure between agents, such as a fact that never reached the agent that answered. FC3 is a failure to verify or to finish, such as stopping early or answering without the facts. `metrics.mast_tag` applies six fixed rules in order and gives each failed run one group:

**6. Why a scripted model and not an LLM?**

No free provider answered from the build machine. The scripted model in `models.ScriptedModel` reasons perfectly over its own prompt and nothing else. So every difference comes from what each design lets into each context and what each protocol costs. A real model adds its own mistakes, and record mode is ready for that run.

**7. Is the scripted model fair to every design?**

It uses the same procedures from `procedures.py` in every role, and it sees the same budget line. The lead plans by splitting directory members round robin, which is a simple, sane plan, not a tuned one. It cannot catch errors, so this study cannot show the case where a checker or a second opinion fixes a mistake. The README says so under Limits.

**8. How did you set the budget levels without tuning on the test set?**

`scripts/dev_budget_stats.py` runs every design on the dev tasks with no cap. The tight level sits at the median use and the loose level just above the largest dev run. `DECISIONS.md` gives the numbers. The held-out tasks ran once, after that choice.

**9. How do you stand in for time?**

Scripted calls take microseconds, so seconds mean nothing. `Run.critical_calls` counts the model calls that must happen one after another. Parallel workers count as the slowest one. That is the latency a real deployment would feel, minus network time.

**10. Why exact answers?**

They remove the judge. A judge model adds its own errors and its own bias toward longer answers. Every task in `tasks.py` has an answer computed from the structured facts, and `metrics.correct` compares normalized strings and numbers.

**11. How do you know the tasks are answerable?**

`oracle.solve` answers each task through the same tools with no model, following `procedures.next_action`. It gets every one right, and `results/oracle.json` records it.

**12. What results are the most surprising?**

At the loose budget the orchestrator matches the single agent on wide tasks for fewer tokens. Many people expect a team to cost more. The reason is context length: one agent pays again for every document in its history on every call.

**13. What does the pipeline lose?**

Its checker sees only the executor's answer and evidence. In both loose runs that failed, the executor's slice of the budget ran out while it wrote its answer with the evidence. In T17 that answer was right. The cut output was not valid JSON, so the checker got nothing and answered from what it could read in its own small share. Run `splitbench show T17 pipeline loose` to see it. Those runs are the pipeline's FC2 failures at the loose budget.
